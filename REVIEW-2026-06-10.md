# LibEphemeris Full-Project Code Review — 2026-06-10

## Scope & methodology

Twelve parallel deep-review passes covering the entire hand-written codebase (~90K lines; the ~295K lines of generated coefficient tables were inspected structurally only):

1. Core dispatch (state, context, planets, fast_calc, astrometry, erfa_nutation, cache)
2. API surface, constants, time, utils, IERS
3. eclipse.py — solar half (lines 1–4490)
4. eclipse.py — lunar eclipses & occultations (4487–8035)
5. eclipse.py — rise/transit, heliacal, Besselian (8035–end) + heliacal.py
6. LEB binary format stack + generators
7. Lunar theory (lunar.py, true_node_terms, generated correction tables)
8. Houses, angles, crossings, Arabic parts
9. Fixed stars, refraction, extinction, Schaefer
10. Minor bodies, SPK, downloads, hypothetical bodies
11. Horizons backend, planetary moons, moon theories, rebound/astropy integrations
12. CLI, dev CLI, config, packaging, test infrastructure, docs

Verification: items marked **verified** were checked live against pyswisseph 2.10.03 (project venv, Moshier mode where applicable), against pyerfa, against NASA's published 2024-04-08 Besselian elements, or by pure-math replication of the code's formulas. No project test suites were run; no repository files were modified (this report file excepted).

Severity: CRITICAL = wrong results or broken functionality on realistic inputs, or a project-rule violation with legal exposure. MAJOR = verified deviation from the 1:1 pyswisseph mandate, silent wrong results in edge paths, or thread-safety/robustness holes. Counts: 10 critical clusters, ~45 majors, ~70 minors, ~40 nits.

---

## Executive summary

The heavily-exercised core is excellent and demonstrably 1:1 with Swiss Ephemeris: `constants.py` passed a full automated AST diff against pyswisseph with **zero mismatches**; `julday`/`revjul` are exact across ±7M JD; tropical house cusps match to ≤1e-6° across 25 systems × 130 latitude/ARMC grid points; crossings match to 0.001–0.16 s; solar-eclipse maxima are within 10 s of NASA; LEB numerics (Clenshaw, derivative scaling, LEB2 round-trip) verified bit-correct.

The problems concentrate in three places:

1. **Untested execution paths are broken outright.** The Horizons HTTP backend crashes with TypeError on every fetched-body calculation; auto-SPK downloads never land where they're registered; planetary moons are off by 5–30 AU; Vulcan/Proserpina return heliocentric positions as geocentric. None of these paths have real test coverage (the Horizons tests cover only analytical bodies; SPK tests mock the download), and there is **no CI**.
2. **Secondary outputs systematically break the 1:1 mandate.** Tuple shapes are right, but retflag bits, attr cells, visibility flags, search-direction semantics, star-name syntax, cusp speeds, and sidereal ayanamsha handling deviate from pyswisseph in dozens of verified ways.
3. **A systemic error-swallowing pattern** (broad `except` returning zeros/sentinels) defeats the library's own LEB→Skyfield fallback design and converts ephemeris-range errors into silent garbage.

Plus one project-rule violation with legal weight: several house-system routines are documented and structured as direct **swehouse.c translations**, violating the explicit independent-derivation requirement.

## CRITICAL findings

### C1. Lieske precession coefficients transposed — corrupts all FLG_J2000 output for node/apogee/Uranian bodies at historic dates
`libephemeris/astrometry.py:393-395` — `zeta` and `z` have their quadratic/cubic coefficients exactly swapped vs Lieske 1977 (ζ: 0.30188/0.017998; z: 1.09468/0.018203). Verified against `erfa.pmat76`: 0.96″ error at the medium-tier edges (±5 cy), 61″ at 20 cy, 906″ at 50 cy. This is the live path for every FLG_J2000 ecliptic output of nodes/Lilith/IntpApog/Uranians/Transpluto (`planets.py:1481-1484, 2012, 2060, 2086, 2135`; `fast_calc.py:819-835`). LEB-vs-Skyfield comparison tests cannot catch it because **both backends share the bug**. Fix: swap the coefficients back (and add the missing t1 epoch terms), or derive from `erfa.pmat06` since pyerfa is a hard dependency.

### C2. Horizons HTTP backend is non-functional
- `horizons_backend.py:642-643` (also 624/625/638/639) — `_to_ecliptic_output` passes tuples into fast_calc helpers that take scalars (`_cartesian_to_spherical(x, y, z)` etc.) → **TypeError on every fetch-based calculation**. `planets.py:902/1024` catch only KeyError, so users get a crash, not Skyfield fallback.
- `horizons_backend.py:569,575-583` — deflection constant wrong by ~3.0×10⁶ (GM in km³/s² mixed with c in AU/day), formula not perpendicular to line of sight, and the `dot_eq > 0.9999` skip excises the near-conjunction region where deflection peaks.
- `horizons_backend.py:647,708,733` — `from .ayanamsha import get_ayanamsha_ut`: module doesn't exist (real function is `get_ayanamsa_ut` in planets.py). Any FLG_SIDEREAL request in horizons mode crashes — including on the analytical paths that otherwise work.
- `horizons_backend.py:154-167` — VECTORS query omits `REF_PLANE`; Horizons defaults to ECLIPTIC while the pipeline assumes equatorial ICRF → 23.44° frame error once the TypeError is fixed. Add `REF_PLANE='FRAME'`.

Only analytical bodies (nodes, mean apogee, Uranians) work — exactly the subset the tests cover.

### C3. Auto-SPK download path contract broken
`spk_auto.py:1414-1426, 526-535` — `_download_spk_astroquery` delegates to `spk.download_spk(path=output_dir)`, which writes `{body}_{YYYYMM}_{YYYYMM}.bsp` and returns that path — but both callers discard the return value and assume their own naming (`{body}_{jdstart}_{jdend}.bsp` / `{body}_{md5hash}.bsp`). Consequences: `_find_covering_spk` never matches previously downloaded files (re-downloads from Horizons every call); registration runs on a nonexistent path and raises `SPKNotFoundError`, which `try_auto_download:576` does not catch despite its "never raises" contract; `download_now(force=True)` is a no-op when the file exists. Unit tests mock `_download_spk_astroquery`, hiding all of it.

### C4. Vulcan and Proserpina return heliocentric positions as geocentric
`hypothetical.py:2904-3024, 3434-3496` + `planets.py:2146-2171` — both are computed heliocentric (their docstrings say so) and returned directly as geocentric calc output under a wrong comment. Vulcan: up to ~180° longitude error and unphysical distance (0.137 AU vs ~0.86–1.14). Proserpina: up to ~0.7°. Fix: subtract Earth's heliocentric position exactly as the Uranian/Isis blocks do.

### C5. Planetary moons double-count the parent barycenter (~5–30 AU error)
`planetary_moons.py:487-495` (speeds too at 529-549) — Skyfield's `SpiceKernel.__getitem__` already chains to the SSB, so `moon_xyz + parent_xyz` adds the planet barycenter twice (Io ends up ~10 AU from the SSB with jup365). With a kernel lacking the 0→parent segment, registration raises KeyError instead — the module is broken either way.

### C6. `backwards=True` silently ignored in lunar-eclipse/occultation local searches
`eclipse.py:5591` (`lun_eclipse_when_loc`) accepts `backwards` and never forwards it; `eclipse.py:7093` (`_lun_occult_when_loc_pythonic`) advances forward-only. Verified pyswisseph supports both backward searches. Callers asking for a past event silently get a future one. Relatedly `lun_eclipse_when(backwards=True)` raises NotImplementedError (`eclipse.py:5165-5168`) while the fully implemented `_find_previous_full_moon` sits unused.

### C7. Error swallowing silently fabricates results and defeats the LEB→Skyfield fallback
The wrapper `_call_with_leb_skyfield_fallback` (`eclipse.py:94`) is well designed, but implementations swallow the errors before it can act:
- `eclipse.py:5917-5918, 5680-5681` — `lun_eclipse_how` paths catch ValueError (including Skyfield's `EphemerisRangeError` subclass) and return `(0, zeros)` → a short LEB file yields silent "no eclipse".
- `eclipse.py:7759-7760, 7791-7792, 7940-7950` — `lun_occult_where` converts the same failures into a 999.0 sentinel separation → bogus `ECL_PARTIAL` with garbage coordinates.
- `eclipse.py:3616-3620, 3674-3679` — `sol_eclipse_how` catches `(KeyError, ValueError, ArithmeticError, IndexError)` and returns zeros; `sol_eclipse_where` isn't wrapped at all and its `get_separation` returns sentinel 999.0 (`eclipse.py:2999-3006, 3036-3043`), corrupting the gradient search.
Fix: let LEB out-of-range errors propagate to the wrapper; raise the project's `EphemerisRangeError` for genuine range failures.

### C8. swehouse.c-derived code violates the independent-derivation rule (provenance/licensing risk)
- `houses.py:2411` — `_houses_savard_a` docstring literally says "Algorithm (from Swiss Ephemeris swehouse.c):" with swehouse.c variable names (xs1/xs2/xh1/xh2/fh1/fh2).
- `houses.py:4567-4692, 4741-4817` — `_house_pos_pythonic` P/G/K/R/C branches reproduce `swi_house_pos` structure with its exact identifiers (mdd, mdn, sad, san, adp, admc, samc, dfac, VERY_SMALL…); the Koch comment block 4747-4754 is swehouse.c's formula verbatim.
- `houses.py:3900-4098` (Sunshine/Makransky), `houses.py:4255` (`_apc_sector` keeps swehouse.c's signature/structure), `houses.py:3515` (Krusinski pipeline incl. the `swe_difdeg2n` idiom).
Swiss Ephemeris is AGPL/commercial dual-licensed; the project's own rule is "results 1:1, algorithm independently derived." These need re-derivation or an explicit provenance/licensing decision. (Everywhere else, reviewers specifically checked for translation smell and found genuinely independent implementations — this is the one cluster that fails.)

### C9. Star catalog contains corrupt entries (positions wrong by degrees)
- `fixed_stars.py:1671-1681` — "Tarf" (beCnc): RA 130.821442° vs true 124.12884° (+6.7°); dec is beta Cnc's, but pm and HIP 42911 belong to **delta** Cnc.
- `fixed_stars.py:1887-1897` — "Eta Piscium": RA 18.437089° vs true 22.871° (−4.4°).
- `fixed_stars.py:1898-1912` — "Alrescha" mixes alpha Psc position with eta Psc proper motion and eta Psc's HIP 7097.
Any fixstar query for these returns positions wrong by degrees. Re-derive from sefstars.txt/SIMBAD.

### C10. LEB robustness cluster: corrupted files crash through every guard; shared decompressor unsafe; empty nutation evaluated as garbage
- `leb_reader.py:194` / `leb2_reader.py:93` — constructors catch `(OSError, ValueError, KeyError)`, but truncated/corrupt files raise `struct.error`, `zstd.ZstdError`, `ZeroDivisionError` (`leb_reader.py:365`), `IndexError` (`leb2_reader.py:195`) — none caught anywhere in the stack: no Skyfield fallback (`state.py:536`, `planets.py:885`), and `download._is_valid_leb` (`download.py:1318-1325`) raises instead of returning False.
- `leb_compression.py:176-177, 270` — module-level `ZstdDecompressor` singleton shared across threads; python-zstandard forbids concurrent use of one DCtx. Two threads cold-loading chunks race → corruption/crash. No lock exists in any LEB module.
- `generate_leb.py:2514, 2597-2615` + `leb_reader.py:235-238, 441` — `--skip-aux` writes an empty nutation section; readers treat presence as data: `eval_nutation` clamps `seg_idx` to 0 and unpacks the adjacent Delta-T bytes as dpsi/deps (~2.4e6-magnitude values), silently corrupting every position via `fast_calc.py:696`. Reachable through the documented `--merge` workflow.
- `leb2_reader.py:197-206` — `uncompressed_size` from the file is trusted as zstd `max_output_size` → crafted file can demand multi-GB allocations. The value is derivable; validate at parse time.

## Cross-cutting themes

1. **Coverage decides correctness here.** Everything with strong test pressure (constants, julday, tropical houses, eclipse maxima, LEB round-trip) verified excellent; everything without (Horizons HTTP, SPK auto-download, planetary moons, fictitious 49–54, heliacal details, secondary attr/retflag cells) is where every critical lives. The missing CI and the broken `smoke`/`vs-skyfield all` commands compound this.
2. **Systemic error swallowing.** Broad `except` clauses returning zeros/sentinels appear in eclipse.py (both halves), planets.py, fast_calc.py, spk.py, horizons_backend.py — repeatedly defeating the carefully-designed LEB→Skyfield fallback and converting range errors into silent wrong answers. Worth a single dedicated sweep: catch narrowly, raise `EphemerisRangeError`, never fabricate output.
3. **Thread-safety story weaker than documented.** Unlocked lazy singletons (state.py), module-global `_active_reader` + underkeyed frame cache (fast_calc), shared zstd DCtx, spktype21 instance work-arrays, refraction profile cache, planetary-moon registries. Either lock them or scope the thread-safety claims.
4. **Exception-type parity.** Many "not found"/failure paths raise bare `RuntimeError`/`ValueError` instead of the project's `Error`/`EphemerisRangeError` hierarchy (eclipse searches, crossings, spk range). pyswisseph raises `swisseph.Error`; callers catching the compatible `Error` miss these.
5. **Docstrings/comments contradicting code** are pervasive (tret layouts, return shapes, "confirmed by testing" claims that verify false, stale architecture descriptions). In a parity library the docstrings are part of the contract — several documented the wrong behavior as intended.
6. **Duplicated sources of truth**: MOON_* ids (constants vs planetary_moons), pytest config (pytest.ini vs pyproject), GM constants (3 variants in lunar.py), .env parsers (×3), ascmc dispatch (~250 duplicated lines in houses.py).
