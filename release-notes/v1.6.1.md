## Headline: Fix for inverted `is_day_chart` 2D logic (issue #1)

LibEphemeris 1.6.1 fixes a bug in `arabic_parts.is_day_chart()` where the
2D ecliptic comparison treated the lower hemisphere (houses 1-6, below
horizon) as the upper hemisphere, and vice versa. Reported by @Blu in
GitHub issue #1.

No API changes. Fully backward-compatible at the call-site level.

### Bug fixed

`is_day_chart(sun_lon, asc)` previously returned `True` when the Sun was
in the arc from ASC to DSC going counter-clockwise (increasing longitude
through IC) — that is, in the **lower** hemisphere — and `False` when
the Sun was in the **upper** hemisphere through MC. The 3D method,
`_is_sun_above_horizon_3d`, was already correct.

**Example demonstrating the inversion** (from the issue report):

```
ASC = 153°, DSC = 333°, Sun = 352°
Sun at 352° is between DSC=333° and ASC=153° (going CCW through MC=0°),
so it is above the horizon → day chart.
3D method:  True (correct)
2D method:  False (incorrect, before fix)
2D method:  True (after fix)
```

### Affected functionality

This bug affected any code path that determined sect using the 2D
method (no geographic coordinates, or `|geo_lat| ≤ 60°`):

- `arabic_parts.is_day_chart(sun_lon, asc)` direct calls
- `arabic_parts.calc_all_arabic_parts()` Pars_Fortunae and Pars_Spiritus
- `calc_ut()` with `PARS_FORTUNAE` or `PARS_SPIRITUS`

For most real-world charts, this means the previously-computed
**Pars_Fortunae** value was actually the correct **Pars_Spiritus**, and
vice versa.

### Impact on user code

If you store Arabic part values computed with v1.6.0 or earlier, they
must be recomputed with this version. Otherwise the day/night
classification (and the resulting Fortune/Spirit values) was inverted
for most charts.

### Fix details

The 2D comparison was rewritten as a single formula in
`libephemeris/arabic_parts.py`:

```python
# Lower hemisphere (below horizon, houses 1-6) is the open arc (ASC, DSC)
# going counter-clockwise (increasing longitude through IC).
# Boundaries: Sun on ASC (sunrise) or DSC (sunset) count as day chart.
sun_rel = (sun_lon - asc) % 360.0
return not (0.0 < sun_rel < 180.0)
```

This is geometrically equivalent to checking that the Sun is in the arc
from DSC to ASC going counter-clockwise through MC, with inclusive
boundaries.

### Tests added

- `test_issue_1_regression` — verifies the reporter's exact case
- `test_sun_near_mc_is_day` / `test_sun_near_ic_is_night` — parametrized
  across 10 ASC values, asserts MC and IC always have the correct sect
- `test_symmetry_180_rotation` — proves the formula is invariant under
  joint 180° rotation of ASC and Sun
- `test_complementary_offsets_opposite_sect` — verifies that
  complementary offsets from ASC produce opposite sect (away from
  boundaries)
- `TestIsDayChart2D3DAgreement` — verifies 2D and 3D methods agree for
  Rome (lat 41.9°N) and Buenos Aires (lat -34.6°S) at 4 months × 4-8
  hours, with sub-arcminute horizon cases skipped
