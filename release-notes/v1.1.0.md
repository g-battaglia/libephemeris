# LibEphemeris 1.1.0 Release Notes

**Release date:** 2026-04-21
**Author:** Giacomo Battaglia
**License:** AGPL-3.0-only
**Python:** >= 3.12

---

## What 1.1.0 Adds

LibEphemeris 1.1.0 extends the ecliptic-longitude crossing primitives with
a `backwards=True` flag on the three families that previously searched
only forward in time: Sun, Moon, and lunar-node crossings. It mirrors the
existing `swe_helio_cross_ut` behavior, bringing the API surface to full
symmetric step-forward / step-back parity.

This release is fully backward-compatible. All existing calls continue to
work unchanged; `backwards=False` is the default.

---

## Highlights

- **Native backward search on six crossing primitives.**
  `swe_solcross_ut`, `swe_solcross`, `swe_mooncross_ut`, `swe_mooncross`,
  `swe_mooncross_node_ut`, and `swe_mooncross_node` all accept a
  `backwards: bool = False` keyword. When `True`, the Newton-Raphson
  search (with Brent fallback on near-station paths) steps backward from
  the given JD and returns the most recent past crossing rather than the
  next one.

- **Sub-second-offset backward search now correct.** A pre-existing dead-
  zone guard on the backward path was wide enough to collapse
  legitimately-nearby results into full-cycle jumps when the caller was
  within 86 s of a solar/lunar crossing or 86 s of a node crossing. The
  dead-zone is now calibrated against Newton-Raphson tolerance
  (`1e-6°` for sol/lunar; direct `|latitude| < 10 × NR_TOLERANCE_MOON`
  detection for nodes), so a `backwards=True` call issued seconds after
  a crossing returns that crossing instead of the one a full cycle
  earlier.

- **New regression suite.** `TestJustAfterCrossing` (11 new tests)
  pins the sub-second behavior in place. Total coverage in
  `test_crossings_backwards.py` grows from 19 to 34 tests.

---

## Why

Planetary-return search — the motivating use case — requires symmetric
forward and backward navigation. A user viewing their solar return for
2026 and clicking "previous" expects to land on their 2025 return. Prior
to 1.1.0, callers had to simulate backward search by offsetting the
start JD by one mean tropical year / sidereal month / half nodal month
and relying on forward search to snap to the previous event. That
approach:

- Fails near cycle boundaries, where a forward search from an
  interpolated offset can land on the *same* event instead of the
  previous one.
- Is unreliable for the lunar node, whose interval between successive
  crossings varies by about a day across the 18.6-year regression
  cycle.
- Fails completely when the caller's start JD is already *at* a
  crossing — exactly the round-trip scenario produced by the planetary-
  return navigator, which feeds the previously-computed crossing back
  in to search for its predecessor.

A native `backwards=True` flag resolves all three problems and matches
the API shape that `swe_helio_cross_ut` has offered since 1.0.

## API

```python
# Solar / lunar: target longitude + start JD
jd_prev_sun  = swe.solcross_ut(target_lon, jd_start, backwards=True)
jd_prev_moon = swe.mooncross_ut(target_lon, jd_start, backwards=True)

# Lunar node: start JD only (target latitude is implicit zero)
jd_prev_node, lon, lat = swe.mooncross_node_ut(jd_start, backwards=True)

# TT variants follow the same pattern
jd_prev_sun_tt  = swe.solcross(target_lon, jd_start_tt, backwards=True)
jd_prev_moon_tt = swe.mooncross(target_lon, jd_start_tt, backwards=True)
jd_prev_node_tt, lon, lat = swe.mooncross_node(jd_start_tt, backwards=True)
```

All six functions preserve their existing return types and precision
guarantees (sub-milliarcsecond convergence, round-trip residuals below
~0.1 s of JD).

## Fixed

### Solar/lunar backward dead-zone too wide

The pre-1.1.0 backward path gated the "already at target" case with
`abs(diff) < 1e-3°`. In angular terms that is 86 s of solar motion and
~11 s of lunar motion — large enough that a round-trip call (forward,
then backward from the result) would collapse the backward step into
a full synodic cycle, returning an event one year (or one month) in the
past instead of the just-found crossing.

The replacement logic normalizes `diff` from `[0, 360)` into the signed
range `(-360, 180]`, then applies an `abs(signed) < 1e-6°` threshold.
That threshold sits comfortably above `NR_TOLERANCE_SUN = 2.78e-7°` but
well below the angular motion of either body in 1 s of real time, so
the guard distinguishes "caller is numerically at the crossing" from
"caller is a few seconds past the crossing."

### Node backward rejection window too wide

`swe_mooncross_node_ut` rejected converged results when
`jd >= tjdet - 0.001` days on the backward path. That 86-second
rejection window caused a valid result 1–80 seconds before the start
time to be thrown away, forcing the search to continue into the
previous half-nodal-month cycle.

The fix has two parts:

1. The post-convergence direction guard tightens from `0.001` days to
   `1e-6` days (~0.086 s), accepting legitimate results arbitrarily
   close to the start time while still rejecting the pathological
   "converged on the starting event itself" case.
2. The pre-iteration logic now detects the at-crossing case directly
   via `abs(lat) < 10 × NR_TOLERANCE_MOON` and pre-seeds the Newton-
   Raphson search a full `HALF_NODAL_MONTH` step away in the requested
   direction. This avoids the previous failure mode where the linear
   estimate was dominated by floating-point noise and the Newton
   iteration oscillated between the two adjacent crossings.

## Known limitations

`swe_helio_cross_ut` and `swe_helio_cross` carry the same class of sub-
second backward dead-zone behavior (threshold `1e-5°`, which converts to
~10 seconds of Jupiter motion, ~25 seconds of Saturn motion, and up to
~3.6 minutes for Pluto). It is not fixed in this release because:

- A proper fix requires per-planet (or time-domain) threshold
  calibration; a single angular threshold cannot simultaneously satisfy
  Mercury (which needs a loose threshold) and Pluto (whose motion in
  one second is below the Newton-Raphson tolerance).
- The helio function lacks a post-convergence direction guard analogous
  to the one on `swe_mooncross_node_ut`; adding one is part of the
  proper fix.
- Shrinking the helio dead-zone would also shrink the Brent-fallback
  search window for slow planets, breaking an orthogonal code path.

No production consumer of `backwards=True` helio search is affected by
the current behavior: the in-app planetary-return navigator — the only
active caller — serializes timestamps at millisecond precision, which
falls deep inside the existing dead-zone and produces the intended
full-cycle backward step. The edge case is reachable only by external
API clients computing helio crossings at sub-second precision
externally and submitting timestamps within a few seconds of those
events. A tracking issue will be filed against this release.

## Compatibility

Fully backward-compatible with 1.0.x. All existing code continues to
compile, import, and run unchanged. `backwards=False` is the default
value on every affected function, so callers that omit the keyword see
identical behavior to the previous release.

## Upgrade notes

```bash
pip install --upgrade libephemeris==1.1.0
# or
uv add libephemeris==1.1.0
```

No code changes required. To start using backward search:

```python
import libephemeris as swe

# Previous solar return for a given natal Sun longitude
jd_prev = swe.solcross_ut(natal_sun_lon, jd_current, backwards=True)
```
